Sticker document fallback native regression

Scope
The supplied screenshots show a sticker rendered as an Unknown.file document on
macOS, but do not supply its bytes, MIME type or TelegramMediaFile attributes.
The test does not infer these from the displayed file size. It proves a narrower,
source-backed candidate: a file marked .Sticker, with image/webp MIME, no animated,
video or audio attributes, and a size from 300 KiB through 512 KiB inclusive.

Pinned TelegramCore isStaticSticker rejects size >= 300 KiB. The pinned iOS
ChatMessageItemImpl separately allows .Sticker through 512 KiB. The macOS row
factory otherwise selects ChatFileMediaItem; missing FileName produces the
literal Unknown.file. A ChatUI-internal isChatStaticSticker accessor preserves
all existing isStaticSticker cases and adds only the bounded candidate. No core
predicate, hub API, manifest, localization or persistent data changes.

Run
python3 -I tools/tests/sticker-document-fallback/run.py \
  --source-root /absolute/path/to/checkout --output /absolute/path/to/output

Optional --dependency-root selects a materialized checkout containing
core-xprojects/libwebp/build/libwebp-master/src/webp and build/<architecture>/{
libwebpdemux.a,libwebp.a,libsharpyuv.a}. It defaults to --source-root; a sparse
checkout must pass a read-only materialized dependency root explicitly. No graph
build is invoked. Baseline app sources and the pinned core Git object store are
resolved from the harness repository, independent of --source-root. The current
source-root may therefore be a materialized integration checkout without .git.
Pinned core objects must exist in the harness repository's shared submodule
object store or initialized submodule. Reads do not use accounts or databases.

All native compilation acquires fcntl.flock. --compiler-lock defaults to
<output>/compiler.lock for standalone use. A concurrent batch MUST pass its
single shared lock explicitly to every runner. Outputs and lock paths are
validated to avoid writing into source or dependency checkouts.
Swift compilation uses -j1. Objective-C compilation runs one command at a time.
The lock is released in finally. Only generated sources, objects, binaries and
logs are written below --output. Compiler module caches there are removed after
the run. Python runs in isolated mode; no account, keychain, preferences, network,
Telegram GUI, screenshot capture, app launch or payment operation is involved.

Source fidelity
Baseline app revision: 246e3e957ae5cea1ecff6d7a6a6db3e47be69bb5
Pinned TelegramCore: 24638bc69bd083981b178dd1e7f921eebbf7fc46

The runner extracts the exact pinned core getters for fileName, isSecretChatTgs,
isSticker, isStaticSticker, isAnimatedSticker, isAnimated, isVideo,
isInstantVideo, isVideoSticker, isCustomEmoji, isVoice and isMusic. Attribute enum
cases, video flags, media namespaces and dimensions logic are also source-derived.
These are NOT replaced by convenient test booleans. Metadata/storage containers
are in-memory doubles; Postbox coding and FlatBuffers are not exercised.

The app code extracted for both variants covers the full file branch of the row
factory, row sticker status, the file branches of bubble and overlay decisions,
caption suppression, preview choice, file sizing, content-node choice, inner
sticker renderer choice, fallback file naming and sticker resource selection.
The baseline is extracted from the exact pinned app commit; the fixed variant
uses source-root files (unmaterialized unchanged sparse files come from the pin).
Both compile independently and run the same assertions. Public access modifiers
are removed only to allow these excerpts and the test shells in one module.

UI rows and views are inert native class shells, not running AppKit UI. Message,
entry, context and resource containers are doubles. Non-file media branches of
layout and row creation, asynchronous work, menus and view lifecycles are not
executed. HTML document loading is outside scope: its exact eligibility function
is compiled and a precondition verifies no fixture can enter that path before
using the file fallback. No fixture uses HTML MIME/filename.

Checks
Boundary values 300 KiB - 1, 300 KiB, 512 KiB and 512 KiB + 1; nil size; missing
dimensions/thumbnail; cloud and secret file namespaces; absent/present FileName;
ordinary small/large WebP documents; unsupported PNG/GIF/binary MIME with Sticker;
custom emoji without Sticker; animated/video/audio attribute controls; named TGS,
unnamed oversized TGS, secret TGS exclusion and WebM video sticker.

For candidate stickers the test checks row class, bubble suppression, sticker
state, overlay, no caption, 208-point aspect-fit geometry, native static renderer,
static preview, full/thumbnail resource selection and explicit file-layout optout.
The exact baseline must compile and fail the 40 named candidate assertions, with
all negative controls passing. Compile errors do not count as a negative control.

Native decoding
The pinned libwebp.m and WebPImageCoder.m are compiled, unmodified, against the
read-only materialized native codec archives. Source and archive SHA-256 hashes
are recorded. A deterministic 512x256 lossless WebP is encoded in memory; its real
payload is 393296 bytes with the tested archive, within the candidate range.
The exact fetchCachedStickerAJpegRepresentation decode expression invokes the
production convertFromWebP implementation and its actual WebPImageDecoder. The
image is converted to PNG in memory with ImageIO, loaded through NSImage as the
sticker path does, and drawn into a 208x104 memory context. Empty data is rejected.
No network download, cache database or cached file writing is simulated as real.
The decoder enforces pixel/dimension bounds, not a 300 KiB encoded-size gate.

The resource pipeline was also inspected: ChatStickerContentView calls
chatMessageSticker with fetched=true; StickerImage chooses file.resource for a
full-sized sticker and CachedStickerAJpegRepresentation for decoding;
fetchCachedStickerAJpegRepresentation waits for complete data and imposes no
300 KiB gate. PNG conversion and native drawing are executed, but the surrounding
signals, account/media-box fetching and cache persistence are source-inspected.

Remaining boundaries
This is not a reproduction of the exact supplied file. A different MIME, absent
Sticker attribute, malformed bytes, size above 512 KiB or animated attributes
will retain the existing behavior; those cases must not be guessed from a UI size.
Real-window appearance, loading transitions, clicks, Favorites RPCs and acceptance
need the user's manual test in the combined client.

The chat context menu already uses isSticker for Favorites and View Sticker Set;
this change neither creates nor alters those actions. Save As still uses the
original resource and MIME/filename-derived extension; no export bytes change.
The added cases use the native static renderer, not the animated WebP player.
Files carrying Animated, Video or Audio attributes retain their old player/row.
The shared StickerMediaContentView can also be used by previews/pickers; an eligible
file passed to it now chooses the same static renderer. A WebP animation lacking
an Animated attribute is not detected by inspecting payload bytes in this fix.

Core isStaticSticker intentionally remains unchanged, so existing shared checks
outside ChatUI can still differ: MessagePermissions.canEditMessage/canFactCheck,
MessageAppOnlyExtensions.possibilityForwardTo, and EditMessageModel's thumbnail
branch still see a >=300 KiB file as non-static. This patch fixes chat rendering,
not those independent menu/edit/forward policies, search indexing or exports.
