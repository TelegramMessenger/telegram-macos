# Implementing Telegram App Events in a client

This is the contract a client implements. Read [RULES.md](RULES.md) first for the naming rules; this file covers behavior. When this file and RULES.md disagree, RULES.md wins for names and this file wins for behavior.

macOS contains the reference implementation under development (Swift, `packages/AppAnalytics` in the macOS repo). [examples/macos-peer-info-visibility.md](examples/macos-peer-info-visibility.md) shows existing screen wiring, not a complete privacy-safe integration. Read [PLAN.md](PLAN.md) for the current audit and implementation gates. The rules below describe required behavior; the status table distinguishes incomplete parts.

## 0. Collection eligibility comes first

Implement PLAN.md §3 before expanding events. Every producer, recorder, debug hook, queue and transport must enforce an eligible account-bound scope. Secret contexts and descendants are excluded; unresolved context fails closed. The initial macOS policy suspends product analytics across the app while a secret surface is visible. Revocation discards state silently, including late completions and destruction callbacks. A global enable flag or a check of the outgoing `peer_type` alone is insufficient.

Media-preview handoffs must validate a supplied origin against the receiving chat's account, peer, inherited privacy and edit/forward sources before recording failures, constructing children or opening the preview. Preserve an eligible origin's existing scope; do not replace a revoked origin with a new one. Attaching or reading a preview's media journey must discard it if its scope does not match the preview's context exactly. A hidden/unpresented private preview is still excluded, even before visibility tracking can suspend collection. Analytics rejection must not suppress functional preview presentation or sending.

Direct media and recording handoffs require the same receiving-context validation, including legacy callback fallbacks. Missing original context is unresolved rather than a fresh collection grant. A recording request must be restricted to the receiving scope before preparation failures, schedule/payment steps or submission. Revalidate scheduled media against the original context and the actual destination at date selection; reuse that exact destination for enqueue. Context leases must cover provider construction as well as result delivery. Discarding observation must leave functional sending available.

A multi-part media submission must carry its original context locally with its result token. Separate text, album batches and optional additional text cannot capture fresh collection grants for that task. Validate the receiving interaction and actual destination before recording each part, and preserve the validated context through asynchronous provider delivery. A mismatch discards the whole task and pending groups; it is not a failed batch or a partial success. No context identifier is added to the wire payload.

The submission exposes its original context only while its journey is submitting and the scope remains valid. After completion, discard or revocation it exposes unresolved context, preventing a later batch from using the old grant for an independent message observation. Returning the original context unconditionally after clearing recorder state is insufficient.

Forwarded messages resolved during a text send require a second privacy boundary. Resolve one source snapshot and validate returned source peers, secret-media flags and the loaded destination before constructing the accompanying text sender or its observation. Use that validated context for text and forwarding through delivered results, disposal and permission-alert lifetime. Preserve functional text-before-forward order: a forwarding permission error must not suppress the accompanying text. A private result discards the parent task before either sender starts; purging pending analytics after text completion cannot recall an event already dispatched. Do not emit a pre-lookup forwarding event whose sources have not yet been classified. Earlier scheduling/payment UI and cached composer metadata need their own entry-time classification; the send-time lookup does not retroactively protect them.

Composer context capture must classify active forwarded sources before scheduling/payment descendants are constructed. A nonempty forwarding selection is eligible only when its cached message IDs cover exactly that selection and no cached message contains secret media. Pending, partial or mismatched resolution stays unresolved; a later ordinary resolution must not upgrade an already captured unresolved action. Preserve ordinary analytics for subsequent actions after complete ordinary resolution. Forward-message caches can survive clearing the selected IDs, so inactive cached sources must not exclude an unrelated later action. Editing requires checking the edited message's secret-media flag as well as its peer namespace.

A composer forwarding lookup is preparation, not an accepted send. Own its subscription separately from the eventual send. Reject duplicate preparation, cancel it when deferred-send intent is invalidated, and recheck the captured action at source delivery. Cancellation or completion without a source snapshot discards the parent observation silently and must not clear a draft, arm a send transition or scroll the chat. Arm those effects only after a current source snapshot has been admitted and privacy classified. Release preparation ownership before the send starts so clearing the successfully submitted composer cannot cancel the accepted action. Old disposal must not cancel a replacement request, and a pending lookup must not retain a closed controller.

An active reply subject participates in composer privacy even when the outgoing destination is ordinary. Restrict its source peer and require a matching resolved reply message before granting a context; private media, missing resolution or a mismatched cached reply stays excluded/unresolved. Once captured, an unresolved reply action cannot be upgraded by a later cache result. A cleared reply subject makes its old cache inactive. Apply this in the shared composer capture path so attachment, date, payment and send descendants inherit the same decision; a check only in the final per-message event is too late.

Composer privacy can tighten after capture. Remember handed-off scopes weakly and, when a state update reveals private or unresolved active sources, explicitly exclude those scopes before invalidation callbacks or observer notification. Every context sharing such a scope must become excluded permanently. Active presentation leases and visible screens must update their exclusion immediately and retain it until they end; ordinary generation revocation alone is insufficient. Explicit exclusion also follows the existing policy revocation path to discard recorder state and invalidate pending transport context. Never imply that this can recall an event already dispatched before new privacy information arrived.

Keep the composer scope registry atomic and version its privacy changes. A context classified before a private update but registered afterward must be excluded before capture returns, even if the composer has since become ordinary again. Do not hold the registry lock while invoking policy/recorder callbacks. A fresh independent ordinary action can become eligible after excluded descendants close; an old captured context cannot recover. Generic enable/account generation changes must not permanently label unrelated ordinary scopes private.

## 1. Registry constants

- Source: `generated/events.json`, the fully resolved registry. Every param in it has its `type` and `values` filled in, so you never need to resolve references yourself.
- Generate typed constants in your language from that file: event names, screen ids, menu ids and items, settings, flow ids with their steps and params, and every enum's values.
- Never write an event name, screen id, step or enum value as a string literal in app code. Add it to `events.yaml`, run `tools/tg_events.py lint`, regenerate.

For media-preview additions, `add_paste`/`add_drop` mean the normalized selection changed. The draft `add_paste_unchanged`/`add_drop_unchanged` steps mean a nonempty addition left that selection unchanged and followed the existing no-change feedback path. They preserve the original entry route, selected count bucket, mode, blocker and send retry count. Empty callback lists and text-only paste are not unchanged media additions. Consecutive identical steps coalesce and the normal trace cap applies, so these summaries do not provide exact repeat counts. They are UX evidence, not bot classification.

## 2. Transport

- Send with `help.saveAppLog(events: Vector<InputAppEvent>)`.
- `inputAppEvent.time`: Unix time (seconds, double) when the event happened.
- `inputAppEvent.type`: the event name, e.g. `flow.end`.
- `inputAppEvent.peer`: always `0`.
- `inputAppEvent.data`: a JSON object: common params + event params.
- Queue events persistently before sending. Send in batches of up to 50, every 30–60 s and when the app goes to background.
- Delivery is best effort: a failed request may drop its batch. Never retry in a loop.
- Events need an authorized account; nothing is sent before login.
- Bind work to the initiating account and policy generation. Validate before persistence and recheck eligibility at dispatch; disable and secret-context revocation purge pending product analytics and cancel active requests. Legacy direct callers must pass the same gate.
- Bound event size and total queue count, bytes and age. Batch limits alone do not bound offline growth. Preserve occurrence time when queueing.

## 3. Common params

Added once, by the analytics layer, to every event. Definitions are in `common_params` in the registry.

| Param | Value |
|---|---|
| `platform` | your platform id from `platforms` |
| `schema_version` | `schema_version` of the registry you generated from |
| `app_version`, `build` | the app's version strings |
| `session_id` | random UUID, regenerated on every `app.foreground` |
| `seq` | 0-based counter within the session |
| `layout` | `compact`, `regular` or `wide` |

## 4. Flow recorder

A flow records the steps of one eligible task and sends one terminal summary. Existing screen-flow behavior must match `fixtures/flows.json`; add exclusion/revocation fixtures and separate reviewed contracts for cross-controller journeys. Do not silently change existing event meanings.

### Behavior

1. Only an eligible scope can create an active recorder. Excluded or unresolved scopes return an inert recorder that never stores steps or params. For an eligible flow the clock starts when the flow object is created. Use a monotonic clock.
2. `step(id)`: if the flow is finished, ignore. If `id` equals the previous recorded step, ignore. Otherwise increment `step_count`, and if fewer than 50 steps are stored, store `[id, ms_since_start]`.
3. `set(key, value)`: set a flow param; a null value removes it. `set_if_absent(key, value)`: set only if the param has no value. All setters and steps are inert after exclusion or revocation.
4. `finish(outcome)`: only the first call on an eligible active flow counts. Send `flow.end` with:
   - all common params
   - all flow params that have a value
   - `flow`: the flow id
   - `outcome`: one of `flow_outcomes`
   - `steps`: the stored steps, as `[[step_id, ms], ...]` (ms is an integer)
   - `step_count`: total steps recorded, including ones beyond the cap of 50
   - `duration_ms`: integer milliseconds from creation to this call
5. When the owner is destroyed without `finish`, an eligible active flow finishes with `abandoned`. Revoked or excluded flows are discarded silently, including on destruction.
6. All methods are thread-safe. Data callbacks often arrive off the main thread.

### Wiring a flow to a screen

- For existing screen flows, create the flow when the eligible screen controller is created. The screen owns it. Resolve privacy scope first; do not buffer an unresolved flow while waiting for peer data.
- Set params known up front (`entry`) right away. Set params that arrive with data (`peer_type`, `initial`) with `set_if_absent` on the first data update.
- Record a step in the handler of each user action listed in the flow's `steps`. Record system responses that matter to the journey (`username_taken`) where they arrive.
- Record a step for a user action only after any confirmation: in the confirm handler, not when the alert opens.
- Call `finish(success)` where the task actually completes (the request succeeded), after setting result params.
- A failed save is a step (`save_failed`), not `finish(fail)`, when the user can stay and retry.
- An eligible screen flow ends with `abandoned` when the screen is deallocated. Pushing another eligible screen on top of it does not end the flow; exclusion revokes it silently.
- Never put user content in params or steps: no usernames, titles, links, ids or search text. Invalid setters or unknown steps discard the recorder silently; they must not retain invalid values until finish. A setter whose value is already present must not evaluate its fallback value.
- Capture origin, account and policy scope at the initiating action and carry them through callbacks. Media acquisition route and final send method must remain distinct. Do not infer origin from the current screen at completion.
- New journeys follow a task across child controllers; destroying one child is not task abandonment. Recoverable errors keep the task active. Define local acceptance separately from remote delivery.

## 5. Screens and menus

Implement screens at the navigation layer, not per screen.

- `screen.show {screen, source, peer_type?}` when a screen becomes visible; `screen.hide {screen, duration_ms}` when it stops being visible. `source` is the previously visible screen id, filled in automatically.
- A screen that is hidden because another screen is pushed on top of it sends `screen.hide`; it sends `screen.show` again when it comes back.
- One object switching to another screen while it stays visible (a chat view opening another chat, a list switching modes) sends `screen.hide` for the old id and `screen.show` for the new one.
- `menu.open {menu, screen, via}` once per opened menu, and `menu.select {menu, item, screen}` before the chosen item runs. Items without a registry id send nothing.
- All visibility/menu rules are conditional on eligibility. Panels inherit the initiating scope. Secret transitions clear visibility/source history silently; no private duration or hide event may be emitted on return. Track ownership per window/account instead of attributing work from a global latest screen.

How macOS does it: every TGUIKit `ViewController` reports `viewDidAppear`/`viewDidDisappear`/`deinit` to `AnalyticsScreenTracker` through `ViewControllerLifecycleHooks`. The screen id is `controller.analyticsScreen` when set (factories, multi-mode controllers) or comes from the class name through `AnalyticsCoverage.screenForClass`, generated from `coverage/macos.yaml`. Windows and system panels that are not view controllers call `screens.showStandalone`/`hideStandalone`. `tg_events.py coverage --tags` checks that every factory, multi-mode and standalone screen is tagged in code.

The `viewWillAppear` hook establishes exclusion before visibility callbacks. The generic modal wrapper reports its own hooks before forwarding appearance to navigation children, and releases its identity after their disappearance callbacks. It does not grant ordinary scopes to children. `ChatController` assigns a namespace-only privacy context during initialization, before peer data arrives. Action handlers capture an account-bound context before asynchronous work; a child receives that same immutable context. `captureContext(..., inherited:)` can only reuse its original eligible scope, never replace a revoked one. Native panels use `beginPresentation()` before delayed opening and release it after the completion callback returns. Unmigrated panel callers receive an unresolved context and suspend collection. Existing public signatures forward to this conservative path for already compiled callers.

### Media task contract under integration

`AnalyticsMediaJourney` owns one `chat.media_compose` flow, independent of any single preview/editor controller. The registry addition is a reviewable draft and is not authorization to enable or ship collection. Construct it at the actual acquisition action with its captured context, entry route, optional known invocation method and explicit source screen. Do not construct it while generating drop hover targets or for plain text paste. Use `selected` with the current attachment count and mode; pass only counts already available to the functional handler. Counts immediately become buckets, including zero. They describe selected input attachments, not generated archive files or queued messages. Use the actual media/file/archive sending mode; `select_archive` records an explicit archive choice without replacing the acquisition route. Preserve this same task when adding media through another route.

Recoverable local acquisition rejection uses `blocked`, followed by `retry` only for an observed retry. For preview send validation, use `submissionBlocked` at the actual rejected return path and `retrySubmissionIfBlocked` once at the next send action. The latter consumes one pending retry; repeated blocker callbacks do not multiply it, and acquisition filtering does not mark the first send as a retry. Child editor/scheduling/confirmation cancellation is a step while a parent preview remains active. A direct-send date cancellation can terminate its parent attempt because no preview remains to resume. Use explicit cancel callbacks; do not infer cancellation from deallocation or generic signal completion. Pass the originally captured context into the date selector and retain it through confirmation lifetime. Explicit acquisition/preview discard uses `cancel`; an observed close without completion uses `close`. Destruction of the task or an unobserved callback discards state silently. It does not infer abandonment.

Before submission, determine the number of local enqueue parts, including the composer and every album batch. Additional text already included in a media enqueue result must not be counted twice. `beginSubmission` returns an optional analytics handle; its presence or absence must never change functional sending. Report each part once using its local zero-based position and `accepted`, `partiallyAccepted` or `rejected`, derived from the actual enqueue result. Message IDs are never passed to analytics. A partial result within one batch remains partial. Duplicate callbacks are ignored; the handle retains the task across preview destruction. Only after every part is known does it emit one summary. All accepted means `success` (local enqueue only); partial or total rejection means `fail` with `submission_result` distinguishing them. A missing/unknown result (`nil`) silently discards the task. Closing the preview after submission cannot terminate the pending task as abandoned or cancelled.

An empty composer explicitly skips its part; skipping every part discards the task. A composer part can have a result group with up to two operations (text and forwarding). A group aggregates actual results before resolving its parent part. Ending or releasing an unfinished group discards the task rather than inventing success or rejection. Result-building closures execute only for eligible, unresolved, valid positions; do not inspect message IDs for analytics outside that closure.

The aggregator admits at most 256 enqueue parts, each with at most two grouped results. Invalid or larger instrumentation inputs discard analytics without changing the send. It stores at most 50 steps, uses one-second timing resolution and caps retry state at the `4_plus` bucket. Scope revocation erases the flow and aggregation state synchronously; delayed parts cannot revive it. Counts in reports are observed eligible terminal summaries, not all attempts, all sends or a bot-detection denominator.

### Story attachment acquisition, preview and batch submission

The original scope and journey pass through file filtering, preview construction and attachment, preview controls, the existing submit method, and every batch result. A caller that already has a clipboard/drop journey keeps it; this handoff does not create guessed routes for legacy callers.

The native-panel callbacks share one resolution gate plus captured Story/composer revisions. Explicit cancellation cancels the journey; unknown nil completion, owner loss or stale navigation discards. Duplicate completion/cancellation must neither open a second preview nor discard an already transferred journey. Empty selection, unavailable files and rejected sizes use existing categorical blockers; partial filtering preserves the remaining task. Paths, extensions, sizes and filenames stay operational data. Revalidate receiving privacy before filtering outcomes or child construction. Unsupported live-stream preview and unavailable preview factory discard observation.

The Story preview companion preserves the journey using the existing preview hook. Its separate composer-send slot is deliberately skipped because Story previews already carry their caption/additional text in media batches and the old Story composer callback was a no-op. Each actual batch owns one result group. Use Sender's observed expected message count, which includes split captions/additional messages, rather than assuming one result per input attachment. Only exact nonzero cardinality can yield accepted, partially_accepted or rejected; missing/incorrect results discard the parent summary. The context covers provider construction, subscription, callbacks and disposal. Private receiving destinations discard analytics while functional sends continue. Legacy batches without a submitted journey stay unresolved; do not emit a completion-only stories.reply event.

This integration supports comparing attachment routes, preview choices, observed filtering and local acceptance. It does not prove human intent or remote delivery. Picker navigation and the presented preview now carry the original Story revision. Actual modal/window lifetimes, temporary-file relocation, paid/scheduled batches, other Story acquisition routes, text/sticker sends and native account/privacy transitions still require verification. Do not equate this source integration with whole-Story or whole-app coverage.

A Story preview must also bind its send source before presentation through `ChatUIHooks.bindPreviewSendValidation`. The app bridge accepts only a real PreviewSenderController and installs its validator once; unsupported providers fail closed without presenting. Capture the Story revision before factory construction and retain only weak ownership of the Story controller/interaction. Returning to a previous Story, replacing the peer, closing or losing the owner invalidates the preview. This operational check is independent of analytics eligibility and applies when no journey exists.

The preview validates before initial send, both app-file and batch send entries, delayed payment/purchase actions, and every media batch. A false result permanently invalidates that binding and discards observation; later callbacks cannot rebind or revive it. Rejection before submission leaves the preview open and the explicit discard-confirmation path usable. If the source changes reentrantly after one batch was accepted, stop remaining batches, discard the incomplete summary and close through the sent path; do not claim cancellation or undo previously enqueued media. This prevents a stale preview from silently targeting the newly visible Story while preserving original-context privacy handling.

### Explicit forwarding-picker journeys

The draft chat.forward_picker flow measures a forwarding task from an explicit route. Its required entry_point comes from the actual caller: message_selection, message_menu, more_menu, replacement_menu or row_action. ChatInteraction and ChatUIHooks carry this value through additive companions while keeping older signatures. Selected-message forwarding starts before source lookup and carries source_lookup=true; other paths begin with available messages and carry false. Report-mode selection does not start a forwarding journey, and the controller's report branch discards any transferred journey before bypassing picker creation. Callers without explicit route support remain unattributed; message count and current screen never manufacture a route.

ChatForwardSelection owns the pending source journey and request together. Empty selection and duplicate pending IDs start nothing. An observed empty result ends with source_unavailable before a picker exists. A nonempty result records source_ready, which means some source messages are available, not that every selected message was found. Returned peer and secret-media restrictions are applied before this step or the owner callback. Empty completion without a value, selection/location/mode changes, reset, stale completion and owner loss discard silently. Reset checks its generation after disposing old work so a reentrant newer selection cannot be overwritten by the action that caused disposal.

The optional source_coverage field describes a nonempty selected-message lookup: complete means every requested ID was returned exactly once, regardless of order; partial means a unique nonempty subset was returned; unexpected means there are unrequested IDs or duplicates. Empty results already use source_unavailable and omit coverage. Older sourceReady() callers and picker-only starts also omit it rather than guessing complete. The feature compares operational ID sets through a lazy categorical callback evaluated only after policy and loading-stage admission. It retains no IDs, hashes, counts or missing-message lists in the recorder, and rechecks admission after evaluation so revocation cannot restore state.

Coverage is diagnostic and preserves the existing callback's messages and order. A later accepted result still describes local acceptance of the returned batch; partial or unexpected coverage does not become complete merely because that batch was accepted. Compare coverage alongside the terminal result when evaluating whether forwarding fulfilled the original selection. An unexpected result can indicate a lookup bug or stale state; it is not a bot verdict.

The optional journey-aware ChatInteraction companion transfers ownership to ChatController, which hands the same object through the observed factory and attachForwardJourney bridge. The factory uses the context-aware construction path to avoid creating a second recorder, validates the constructed child's context, then attaches under that context. Journey restriction requires the same original scope; a stricter, unrelated or foreign grant discards the observation. The picker setter repeats this check for direct attachment. Older callbacks/factories without the attachment bridge discard the partial source journey; a legacy source-aware picker may then start a picker-only observation with source_lookup=false. Compare these strata separately and do not infer lookup success from their summed counts.

The installed source-aware factory attaches AnalyticsForwardPickerJourney using the constructed picker's validated context. A picker-only journey begins at open_picker; a transferred selection journey includes lookup_source and source_ready first. It then records choose_chat/choose_topic, a typed result or explicit cancellation. Premium/poll restrictions and operational errors retain only the last categorical blocker and capped retry count. A poll marker resets the journey to a retryable stage before its operational error; that error must not replace poll_restriction with operation_failed. Unexplained disposal of a submitted operation discards the observation, while explicit picker closure records cancellation without claiming to undo accepted work.

The picker calls beginSubmission(topic:) and retains its returned cleanup closure for that subscription. Cleanup is correlated with the admitted attempt, so a previous blocked attempt finishing disposal cannot erase a retry started from its error callback. An unadmitted duplicate returns inert cleanup. Attempt identities stay local, are erased with the journey and never enter analytics. Cleanup holds the journey weakly and remains inert after revocation or owner release. Whole-journey submissionEnded() is only suitable when no newer submission can exist.

Destination discovery adds search_used, initialized to false, and at most one search step when a nonempty search state reaches an eligible picker-stage journey. The query-emptiness predicate is lazy and evaluated under the same policy admission as the recorder; private, unresolved, revoked, completed or already-searched journeys do not evaluate it. Query strings, changes, lengths, result counts and titles are not stored. The Boolean survives the bounded step trace filling up, including when first search happens after that limit. It means the picker observed search usage, not that a human typed or chose a search result. Clearing search does not clear this summary.

The optional activation field describes the last admitted submission: row_action, return_key, number_shortcut, saved_messages_shortcut, send_button or send_menu. The shared row callback is not proof of a mouse click; keyboard adapters supply their explicit override. Return paths include the highlighted-row handler and the normal return-key fallback; number shortcuts do not log which number or row index was used. Send-menu scheduling receives its label only when the date callback invokes submission, not when the menu opens. Direct internal submissions lacking an explicit adapter omit activation. A retry replaces the previous value, including clearing it for an unknown route, and a duplicate rejected by operation ownership cannot overwrite the current submission.

Activation is captured and consumed before asynchronous preflight or callbacks can reenter. Forum/community navigation and premium handling clear the temporary override before creating children. This prevents an error-alert retry or nested destination selection from inheriting the old keyboard route. The deferred single-target preflight passes its captured activation into the same typed forwarding branch after metadata completes. None of these categories establishes human input, accessibility usage or automation; do not treat a missing or repeated route as a bot verdict.

Admitted destination-stack changes record open_forum/open_community and back. Reopening the same top destination, backing out of an empty stack or invoking a closed picker produces no navigation step. These steps indicate navigation requests, not loaded content. Forum/community entry restricts the original context before navigation, progress construction and scoped result delivery; a private destination erases previous observation. Search observation is detached on close and owner destruction without stopping the UI-owned search source. Policy serialization protects observation from background search emissions; no raw query is queued by an additional analytics delivery operator.

Interpret results separately: draft_prepared and destination_ready are local preparation/navigation successes; accepted is local enqueue acceptance. None is remote delivery. Terminal source_lookup=true summaries now include observed empty selected-message lookups before picker construction. They do not count all forwarding starts: interruption, missing callbacks and privacy revocation discard, and older bridges may lack source observation. Interrupted recovery, search-empty/error/loading outcomes, native input routing and payment/permission gates outside the reviewed single-recipient branch remain coverage gaps. The model is inert for missing/private scopes and synchronously erases state on revocation. These optional client routes cannot establish human intent or justify restrictions on their own.

### Forwarding picker outcomes

The single-recipient ForwardMessagesObject branch of ShareModalController consumes performObserved results, including the original comment and payment arguments. Its SharePickerResult is draftPrepared for an updated existing draft, destinationReady for new-chat/topic readiness, and accepted/partiallyAccepted/rejected/unknown for actual Saved Messages local acceptance. The legacy Bool callback still reports completion of a usable local draft/navigation action as true, so it cannot be interpreted as a sent-message flag.

Unsuccessful or uncertain terminal forwarding results close with false and show the existing incomplete-sharing notice, which asks the user to check the target before retrying. They do not automatically repeat a potentially partially accepted send. Public-poll restriction is different: its typed marker is filtered without emitting a Bool so the subsequent operational error reaches the existing alert and leaves the picker open for retry. A false first value would be consumed by SharePickerAction.take(1) and hide that error. Closing during metadata or enqueue cancels the owned work and produces one cancelled callback, without claiming to undo core acceptance.

The prepared-message app bridge conservatively maps draft/readiness/missing-source/missing-target picker values to unknown. It cannot tell a mini-app that navigation sent its message. Forwarding uses the separate AnalyticsForwardPickerJourney, preserving these operational distinctions instead of attaching the enqueue-only AnalyticsShareJourney. The quick-target menu captures the original chat/group context and a deferred-action token when its source is built. This creates no analytics task. The distinct chat.quick_forward flow has direct_target/topic_target entry values and no guessed screen. ForwardMessagesObject.performObserved emits typed local facts through the app bridge. Updating an already-current chat’s forwarding IDs is draft_prepared. A newly opened chat or topic becoming ready with an initial forwarding action is destination_ready: the separate invokeInitialAction path has not been observed by this callback, so readiness must not be called draft application or enqueue acceptance. Saved Messages observes actual results: accepted, partially_accepted, rejected and acceptance_unknown remain distinct. No result implies remote delivery. Consumers must not sum all success outcomes as sent messages.

Source/target metadata absence and the known public-poll restriction are categorical outcomes. Completion/disposal without an observed typed result discards the action rather than inventing abandonment. ### Sharing the signed-in user’s contact from a profile

`UserInfoArguments.shareMyInfo` uses its owned `ProfileOwnContactShareAction` and the distinct `peer_info.share_own_contact` flow. This route sends to the profile peer after confirmation; it must not be labeled profile_contact, which opens a destination picker for the viewed contact. Capture and account-validate the original profile context before target metadata construction, restrict the target and every returned peer, and preserve that origin through confirmation, account-contact lookup, enqueue, progress presentation and disposal. Missing, foreign, revoked or private origin cannot become eligible when ordinary metadata arrives.

One pending action covers metadata, confirmation and local enqueue. Install subscription ownership before request construction, check the generation again before subscribing, and consume confirmation callbacks once. Starting contact-picker sharing resets this action; owner release disposes pending work, and stale callbacks cannot send. An explicit dialog cancellation records cancel with cancelled outcome. Unexplained dialog destruction, replacement, owner loss or progress disposal without a terminal result discards silently and releases admission. These paths must not emit abandonment or claim an in-flight contact was undone. Retain the captured exclusion while an obsolete confirmation remains alive.

The action records request, target_ready, open_confirmation, confirm, source_ready and submit. Observed missing target is target_unavailable; missing, non-user or mismatched account contact is source_unavailable. The own-contact lookup uses a safe type/identity check. One non-nil returned message ID means accepted locally, one nil means rejected, and empty completion or incorrect cardinality means acceptance_unknown. Never serialize those IDs or the contact’s names, phone number or vCard. The flow uses the known peer_info source, reviewed categorical result, bounded steps and one-second timing. It has no retry count: a later explicit action after cancellation/dismissal starts a new task, not a claimed retry of the prior enqueue.

This observation can show where an eligible profile action stops; it is not a total-contact-send denominator, proof of human intent, or permission to classify/restrict accounts. The action preserves existing send attributes; paid-message/permission behavior and native confirmation/progress/window/account-switch verification require their own audit. Model and extracted-source tests do not prove native UI or server delivery.

## 6. Screen coverage

Every screen of your app needs an inventory decision, so eligible `screen.show` events mean the same thing on every platform. Mapping a secret or sensitive screen is not authorization to collect it. Screen coverage does not establish interaction coverage; maintain the separate scenario ledger specified in PLAN.md §9.

1. Build an inventory of everything screen-like in your code: controllers, fragments or views that are shown on their own, modals, sheets, windows, system dialogs and pickers. `tools/macos_inventory.py` is the macOS version.
2. Write `coverage/<platform>.yaml` with a decision for each item: a screen id, a list of screen ids (one controller with several modes), or `{ignore: <reason>}` with a reason from `ignore_reasons` (base, container, embedded, placeholder, lab, transient, helper, dead_code).
3. When your app has a screen the registry lacks, add it to `events.yaml` first; do not invent a local name.
4. Make the check fail in CI when the inventory and the mapping disagree, like `tg_events.py coverage` does for macOS.

`coverage/macos.md` lists every registry screen with its macOS sources; use it to find the matching screen in your app.

## 7. Debug support

- Debug builds may log eligible, validated events (type + JSON) to the app log. macOS uses tag `Analytics`. Never log excluded activity or rejected payloads.
- Validate in release builds as well: names, params, types, enum values, flow-specific steps and params, menu/item pairing and size/range bounds. Drop invalid payloads before logging or queueing. Debug assertions can supplement this, not replace it.

macOS validation uses `AnalyticsValidationSpec` generated from the registry. The flow envelope requires `steps`, `step_count` and `duration_ms` in addition to `flow` and `outcome`. Each step is exactly `[registered_id, integer_ms]`, timestamps are nondecreasing and no later than total duration, consecutive identical steps are invalid, and the total count may exceed the stored count only at the 50-step cap. A flow param may declare `outcomes` to restrict which terminal outcomes can carry it. `peer_info.visibility.result`, for example, is accepted only with `success`.

A flow can specify `timing_resolution_ms` (integer 1–60,000; default 1). The recorder rounds elapsed times down to that resolution, and validation rejects finer step or total durations. `chat.media_compose` uses 1,000 ms; existing flow fixture timing remains unchanged.

Integers and milliseconds are finite, nonnegative, exact JSON integers no greater than 9,007,199,254,740,991. Metadata strings are at most 64 UTF-8 bytes and contain letters, digits or `.+-_`; session IDs must parse as UUIDs. macOS fixes platform/schema values and overwrites supplied common metadata with its own values. Encoded payloads are limited to 15 KiB before debug logging, leaving room within the core's 16 KiB operation limit. Non-finite or backwards flow clocks discard the recorder; invalid screen clocks do not emit a duration.

## 8. Definition of done

1. `python3 tools/tg_events.py lint` passes.
2. Your platform's tests run every case in `fixtures/flows.json` and pass.
3. No event names, screen ids, steps or enum values appear as string literals outside generated code.
4. Every screen-like item in your inventory has a decision in `coverage/<platform>.yaml`, and the check passes.
5. In a debug build, using a wired screen prints a `flow.end` line whose data matches the shape in the example.
6. PLAN.md privacy and account-isolation tests pass at recorder, log, snapshot, queue and transport boundaries, including legacy bypasses and concurrent revocation.
7. Every implemented journey has scenario-ledger evidence for its routes, outcomes, cancellation/retry and empty excluded-context trace. Distinguish tested from deferred or unavailable routes.
8. New events answer a documented question and preserve acquisition/submit origin without content or identifiers. Terminal semantics and deduplication are tested.
9. Queue bounds, disable/purge, validation, occurrence timestamps, performance and affected feature regressions are verified. Unrun checks are listed explicitly.
10. Analytics remains disabled until a separate rollout decision; bot-related metrics have no automatic enforcement effect.

### Rich-editor group media context and target continuity

Collage addition, conversion from single media, replacement and image editing preserve the originating context through menu construction, native panels and asynchronous results.
